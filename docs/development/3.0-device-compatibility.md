# 3.0 设备适配：Stats 源码研究与实施边界

日期：2026-10-13。产品基线：2.9.10 Beta70；研究起点：`6499c8d4ca2cce53343f89bb1a2adc5c7e93c80b`。研究分支：`codex/stats-compatibility`。

本轮完成源码对照、固定来源数据、离线目录审计和后续验收场景。本轮没有改变 App、kentsmc、配置、版本号、更新线路或线上资产；没有构建、安装、运行硬件命令或宣称实机适配通过。

## 结论与优先顺序

现有目录已经包含 Stats 固定版本的 **M1～M5 专属温度 key**，包括 M4 和 M4 Pro/Max 不同的 GPU key。当前主要缺口是平台相关的解释、未知读数的可信度、探测失败的恢复，以及底层调速工具的可追溯性。继续追加 key 并不能独立解决这些问题。

建议按以下顺序落实，每一步单独提交和回退：

1. **传感器元数据与离线验收**：先引入芯片平台、明确组件类别和平均资格；已识别平台使用对应定义，未知平台保留已发现温度，不能靠 `Tf` 前缀决定 CPU。先保持现有候选集合和“最热”选择范围，分别验证标签变化与平均值变化，避免一次改变探测、曲线和降级。
2. **探测结果与恢复**：区分成功发现无风扇、读取失败、读取成功但不能确认写入能力；增加有间隔的失败重试和唤醒重新发现。保持串行、防重入和原有缓存时效；不能因一次启动失败永久判定不支持。
3. **风扇后端**：确认或恢复现有 kentsmc 的源码版本后，再适配模式 key 大小写、目标值类型、逐风扇限幅和系统接管。源码无法对应之前，不替换正在工作的二进制，不宣称 Stats 的新控制逻辑已在我们这里生效。
4. **功率与 HID 补充**：功率通道缺失/改名/单位未知需要显式缺失状态；HID 温度可以作为单独来源，先观测，确认含义、时效和去重后再考虑参与控制。

这些建议是研究产物，尚不是产品实现。合成场景通过后仍需 Beta 的实机日志与系统接管验证；发布说明应分别列“代码覆盖”“模拟验证”“实机验证”。当前适配范围保持产品既有 Apple Silicon；Intel 涉及工具架构、安装包和控制路径，不在本轮通过复制传感器表隐式加入。

## 目录对照的实际结果

审计脚本比较本工程 97 个静态 key 和上游 193 个 SMC 温度模板；另外保存 11 个 HID 模板，不把两种读取接口混用。

| 上游平台声明 | 每个变体的专属温度声明数 | 本目录缺少的专属 key | 平台相关名称差异数 |
| --- | ---: | ---: | ---: |
| M1 / Pro / Max / Ultra | 18 | 0 | 0 |
| M2 / Pro / Max / Ultra | 14 | 0 | 4 |
| M3 / Pro / Max / Ultra | 24 | 0 | 0 |
| M4 / Pro / Max | 23 | 0 | 6 |
| M5 / Pro / Max / Ultra | 26 | 0 | 3 |
| 上游 M6 声明 | 30 | 17 | 12 |
| 上游 A18 Pro 声明 | 8 | 0 | 4 |

“声明数”不是设备的实际传感器数量或支持清单。M4 每个变体只计算其适用的两条基础 GPU 声明；不把普通 M4 与 Pro/Max 的四条键同时计入。未计入此表的通用模板也可能存在于设备上，需要实际枚举和验证。

### 同 key 的平台含义

`Tp09` 在 M1 是 CPU efficiency 温区，在 M2/M4 是 CPU performance 温区。当前平面 lookup 取第一条定义，所以会显示 M1 名称，但仍属于 CPU；**这本身是标签/排序差异，不能推断当前温度值或平均值一定错误**。`Tp0X`、`Tg0j` 等也有温区序号差异。

上游一共存在 20 个名称、类别或平均资格随平台变化的 SMC key；其中 `Tp0P` 在 Intel 被标为 Powerboard，在 M1 属 CPU。不能把所有平台的一份扁平表直接用作硬件语义的唯一依据。

平台识别建议用现有 `sysctlString(named:)` 读取 `machdep.cpu.brand_string`，严格匹配支持的 token；不要用 substring 将未来 M10 误认成 M1。硬件能力仍从实际 key 和读写结果判断，不能因为 `hw.model` 不在名称表中就禁用遥测。未知平台上的冲突 key 应标为未知/不确定，保留数值和原始 key，避免冒用某代温区标签。

### 未知传感器与平均值

当前未知 key 的第二个字符为 `p/e/f` 时被命名为 CPU-like，进而通过名称归类为 CPU，参与 CPU 平均。Stats 的 M3 目录却明确将 `Tf14/Tf18/Tf19/Tf1A/Tf24/Tf28/Tf29/Tf2A` 这八个 key 归为 GPU。已知这八个 key 在我们目录中正确归类；风险发生在**新出现、目录中尚未收录的 Tf key**，不是已知 M3 GPU 当前被误归类。

两次读数有效且差值 ≤15℃只能证明短时读数稳定，不能证明该 key 属 CPU/GPU。建议将“温度读数有效”与“组件含义已确认/允许参与平均”分别记录。未知温度继续按现有规则可见、可手动选择；组件平均只采用有平台依据且允许平均的定义。修改平均资格会影响用户曲线输入，必须给 Beta 单独的回归和日志证据。

Stats 的通用 `TC0D/TC0P/TCAD/TG0D/TG0P` 等被明确排除平均；我们目前可动态发现，但没有这种独立标记。是否参与平均是策略差异，应通过期望温区与样本验证后调整，而不是认定所有未平均的上游条目都是无效温度。

### 初次探测与温度异常

Stats 初始化会筛掉零值和 >110℃ 温度；后续 CPU 值 <10 或 >120 则保留旧值，代码说明针对 M2。不能照搬初始化 >110 的门槛，否则可能排除我们需要观察的高温读数；也不能无限沿用旧值却更新新鲜度。

我们已有 0～120℃ 范围、后台批量缓存和 15/45 秒过期分级，必须保留其设计理由。零值/低值是否来自异常，要有 key、平台、读取状态和前值依据；先用合成场景覆盖，不全局用“零值=故障”处理风扇 RPM 和模式。

当前动态 `-l` 一次尝试后即设置 attempted；启动失败或无可用 key 后，本次进程通常不再自动重试。另有屏幕变化时在空 profile 下重新 probe 的路径，但不会清除动态 discovery attempted。因此是一个明确的恢复覆盖缺口，不能表述为所有读取失败都永久不恢复。

建议为 discovery 单独记录失败原因、连续次数、下一次允许重试时间，采用有上限的退避；唤醒时允许重新发现但不并发积压。Stats 的 HID reader 使用正常 60 秒/缺失 5 秒重发现是一个参考，不能直接当我们 CLI 的最佳间隔。

## 风扇工具是另一层能力边界

现有 `kentsmc`：arm64 Mach-O，SHA256 `56b9b4f7239b4b043b8b69c92ed23f184eaf55a6b7d67c419d899da3a7254605`。App 调用 `-r`、`-l`、`--unlock-fans`、`--fan-rpm`、`--fan-auto`；特权命令仍走既有 sudoers/命令执行队列。仓库没有对应工具源码和确定的编译提交。

README 链接 `exelban/kentsmc` 本轮返回 404；公开候选 [helmutschneider/kentsmc](https://github.com/helmutschneider/kentsmc/blob/1a96dc4801727c8546b948bcf88ec62d6ca29e61/KentSMC.swift#L495)固定提交 `1a96dc4801727c8546b948bcf88ec62d6ca29e61` 中未见 `--unlock-fans`，其 fan-rpm 使用大写 `Md` 模式 key 与 Float target。**该公开候选不等于我们二进制的源码**。字符串检索能提示现有二进制含大写模式键/Ftst，但不能证明所有内部路径，也不能凭没找到小写字符串证明绝对不支持小写模式。

| Stats 代码证据 | 本产品应验证的契约 | 本轮结论 |
| --- | --- | --- |
| 先探测 `F0md`，回退 `F0Md`，缓存选择 | 模式 key 按实际硬件能力选；探测失败不能当合法自动模式 | 当前二进制是否支持两种形式未确认 |
| 目标 `F{i}Tg` 分 `flt ` / `fpe2` 编码，不支持类型不写 | 读取 key 元数据后才决定编码；逐风扇限幅 | App 文本接口无法证明底层已做到 |
| 直接写模式优先，失败才走 Ftst；无 Ftst 时逐风扇恢复自动 | 不把 Ftst 缺失等同无风扇；恢复成功需要明确结果 | 后端改造需对应源码及 fake SMC 验证 |
| 模式 0 与 3 均视为自动 | 不能把未识别数值强制解释成手动或自动 | 加入契约夹具，不能仅看 exit=0 |
| 保留 firmware/transport 错误，失败元数据不永久缓存 | 缺失 key、权限不足、临时失败各自有原因并可恢复 | 现有 nil/exit status 细粒度不足 |

Stats 的锁与 SMC 假实现测试可以借鉴。它的最长解锁等待包含 3 秒等待及多次重试，不能塞进我们的 2 秒控制周期或启动主线程。它还对全零数据普遍返回 nil，仅给部分模式键例外；我们的 0 RPM 可表示停转，必须保留。

当前全局转速上限取多风扇有效最大值中的**最小值**，适用于一个目标写所有风扇的设计，不能当 bug 改成最大值。缺少 maxima 时的 4900 回退有既有用途；将其升级为能力不足下限制调速/只读策略，会改变使用行为，需要在后端适配时单独验证。Stats 显示层 min/max 缺失时用 1，不应成为我们控制层默认安全边界。

对 FNum/RPM 文本，建议在转 Int 前验证有限数和范围，限制合法 fan ID，避免极端/损坏数值导致溢出或巨大枚举。这里是输入健壮性建议，没有观察到实际设备触发崩溃。

能力判定应以只读探测为起点，不能启动时为了“测试支持”任意写风扇。用户实际请求调速后，再根据命令结果、可读模式/target 与 RPM 收敛信息判定；target 写入和物理 RPM 稳定是不同阶段，不能用一次 RPM 不一致误判失败。

## 功率与额外传感器

我们的 IOReport 已与 Stats 使用类似 Energy Model 通道名和单位差分策略；首轮无基线、能量回绕用非负保护是已有意图。跨平台需要覆盖缺通道、未知单位、只有 GPU 没有 CPU、睡眠后计数重置等情况。当前 current 能量默认 0，若通道缺失但订阅仍有效，可能在后续显示 0W；必须区分“真实 0W”和“未获取通道”。这不直接控制风扇，但可能影响异常提醒，应单独检查提醒服务对缺失字段的处理。

Stats 还读 HID 温度，接口和名称不是 SMC key。可作为新设备的补充数据源，但可能与 SMC 同一温区重复；不要混入平均造成重复加权，不沿用 HID 的宽范围作为我们的控温范围。先输出来源、原始名称、时间戳和支持状态，再决定是否接入选择器。

## 必须保留的现有行为

- 2 秒命令节流、in-flight 防并发、50/75/150 RPM 阈值、0.3 平滑、110℃ 当前临界策略；本轮不借适配改曲线。
- 20 秒启动宽限、连续缺失门槛 5、温度快照 15/45 秒分级、尝试 2200 RPM 后的系统自动兜底。它们是项目明确策略，不用 Stats 的显示逻辑代替。
- 手动选择失效回退最热；CPU/GPU 平均没有合格数据时返回 nil 并进入缺失处理；不把缺组伪造成 0℃。
- profile 中 `hasProbedHardware` 在 refreshTelemetry 之前，防递归；动态枚举后台执行，避免重现启动主线程卡住。
- 历史 semaphore/额外线程超时包装造成读取停滞且已回滚，本轮不恢复。若处理 `-l` 大量 stdout/stderr 的管道背压，应通过假子进程验证并发排空和生命周期，不能用旧超时包装掩盖问题。
- Beta/stable/legacy 线路、安装器系统完成页、反馈邀请框、既有用户配置与真实启动流程不属于设备适配改动。

## 无实机时的验收方式

[合成验收场景](stats/acceptance-scenarios.json)记录输入、期望和证据来源；它们目前是实施要求，没有产品测试执行结果。后续将读取与写入抽出最小 backend 接口，以假后端执行**同一套产品决策代码**，避免另写一套 Python 控制器然后声称验证了 Swift App。

至少覆盖：跨平台同 key、未知 Tf、M2 零温、fanless 与读取失败、0 RPM、两风扇不对称上限、模式大小写、无 Ftst、未知 target 类型、部分恢复失败、最初失败后恢复、过期缓存与唤醒、缺失功率通道。真实调速验收还须验证权限、写入失败、系统接管、退出/重启恢复和实际温度/转速变化，不能由夹具代替。

首个适配补丁建议只落传感器元数据及平均资格，保留候选发现和原始最热策略；后续探测/后端各自独立。不要同时机械拆分整个 main.swift、换后端、换温度范围、调整风扇曲线和发布新包。
