# MacBook 睡眠/合盖后的风扇控制恢复

日期：2026-10-13。基线：Beta70 源码，研究分支 `codex/stats-compatibility`。

维护者本轮明确：用户遇到的表现是**启动正常，睡眠或合盖后失效**。目前没有这些用户的具体芯片、macOS、App build、风扇模式或前后日志。因此可以确认代码的恢复覆盖缺口，不能把它直接当作所有历史反馈的已确认根因。

## 当前风扇逻辑确实存在

主程序先识别风扇与上下限，调用解锁，再按 2 秒周期计算曲线或手动目标；下发前做限幅、2 秒节流、in-flight 检查、50/75/150 RPM 变化阈值和 0.3 平滑。命令失败尝试交还系统。详情见 main.swift 的 `refreshHardwareProfile`、`unlockFans`、`startAutoControlLoop` 和 `setFanRPM`。

不能把平滑和变化阈值本身当成 bug；它们减少无意义的写入与转速抖动。`lastSetRPM` 首次从实际转速初始化也有明确历史理由：避免从零骤降后再爬升。问题是“用于平滑的上一转速”与“本次生命周期仍持有控制权”没有独立状态。

## 与反馈吻合的路径

| 步骤 | 实际代码 / 条件 | 结果 |
| --- | --- | --- |
| 正常下发 | 命令成功，保存 `lastSetRPM = 3000` | 后续用它进行平滑和去重 |
| 睡眠后外部控制状态改变 | 假设系统重新接管；需要真实日志确认 | App 内的 lastSetRPM 仍为 3000 |
| 唤醒 | Sources 中没有注册 `NSWorkspace.didWakeNotification`/`willSleepNotification` | 没有显式使旧控制确认失效或安排接管恢复 |
| 下一周期仍希望 3000 | `abs(boundedTarget - lastSetRPM) == 0` | `below_threshold` 分支返回，没有调用调速工具 |
| 转速/模式与预期不同 | 控制下发判断没有使用实际 RPM、模式 key 或 target 回读 | 目标不明显变化时可能一直跳过恢复 |

上表是基于源码的条件路径推导，**不是实机复现或已经执行的产品回归**。假设系统没有改变控制状态时，跳过相同目标就是合理优化；需要区分两种情况。

屏幕变化处理目前只在风扇数为零或没有传感器时重新 profile，已有完整 profile 的设备不会因此重新确认控制权。而且屏幕改变不等于系统唤醒：外接屏合盖运行、仅熄屏和整机睡眠须分别记录，不能每次屏幕通知都盲目解锁。

另一条已确认的状态覆盖问题是：交还系统先记录状态/展示提示，再调用 `setFanAutoAsync()`，未使用其 completion 来确认成功；退出时也丢弃恢复结果。不能据“已发出恢复命令”宣称实际每个风扇都已交还。这需要与正常退出/更新链路分别验收，不在本轮直接改动。

## 现有二进制已有适配，不应误判为缺失

固定工具 SHA256：`56b9b4f7239b4b043b8b69c92ed23f184eaf55a6b7d67c419d899da3a7254605`。本轮只用 `nm`、`swift-demangle` 和 `otool -tvV` 查看文件，没有执行工具或构建。

静态证据：

| 函数 / 地址 | 观察到的结构 | 证据边界 |
| --- | --- | --- |
| `App.modeKey` / `0x100019a14` | 构造 `F\(id)md` 并尝试读取；后续有 `F\(id)Md` 回退构造 | 证实已有大小写选择路径；未实测所有读取错误的行为 |
| `App.unlockFanControl` / `0x10001a760` | 调用 modeKey、直接模式写入路径、`Direct …=1 failed`、Ftst 读取/写入回退 | 不能笼统说当前工具只会写 Ftst 或不支持直接模式 |
| `App.setManualModeWithRetry` / `0x10001a3c4` | 模式选择与写入重试 | 不能凭有重试就证明唤醒后一定恢复 |
| `0x10001ad74`～`0x10001ad90` | Ftst 路径调用 usleep，参数 3,000,000 微秒；随后 300 次模式重试参数 | 恢复不应在主线程重复调用长解锁路径 |

原始反汇编保存在忽略的 `packaging/pkg/output/stats-compatibility/`。重查方式是对上述哈希对应工具运行只读文件分析。仍缺少确定源码提交，未完成目标类型、逐风扇恢复、所有失败/退出状态的完整审计；不能用局部静态结构保证运行正确。

## Stats 的相关证据

[Stats #2094](https://github.com/exelban/stats/issues/2094)有 MacBook Pro M3 Max 用户报告：系统停转/重新接管后，界面仍保留手动设定，实际没有恢复。该报告与本轮症状相似，是调查线索，不是我们产品的根因证明。

[Stats PR #2924](https://github.com/exelban/stats/pull/2924)处理 M3/M4 的直接模式写入、Ftst 与系统 thermal daemon 协调；作者报告在 M4 Max/M1 Pro 等设备验证，并明确 M2 部分未经测试。当前固定上游 [SMC 实现](https://github.com/exelban/stats/blob/88d5359ad3466efaa16985646a0bb15c6599109f/SMC/smc.swift#L559)已有直接模式优先及 Ftst 回退。我们的二进制也有类似静态结构，因此不应再以“补上同一套解锁函数”为唯一修复。

Apple 的 [didWakeNotification](https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification)和 [willSleepNotification](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification)通过 `NSWorkspace.shared.notificationCenter` 注册。不能在默认 NotificationCenter 注册后假设一定收到；也不应在睡眠回调阻塞等待数十秒解锁。

## 调整后的第一优先级

先实现并验证风扇的生命周期恢复，传感器命名/平均元数据排在其后。建议补丁边界：

1. 记录 sleep/wake 和本次控制生命周期编号；休眠后旧的“已下发成功”不再代表当前控制确认。
2. 保留 lastSetRPM 的平滑用途，单独表示需要重新确认/下发的状态；未知控制权时，不能让“目标差值小”阻止一次恢复。继续遵守串行、in-flight 和写入节流。
3. 唤醒先异步取得本轮新鲜遥测；不直接拿睡前缓存控制，也不把缓存清零当真实 0 RPM。重新获得控制后从实际转速平滑接近当前配置目标。
4. 睡前在途命令的回调不能确认唤醒后的控制权；快速多次睡眠/唤醒不能积压多条恢复任务。
5. 将解锁结果、命令结果、模式/target 可读确认和物理 RPM 收敛分开记录。只在需要恢复时进入后端协调，不每两秒重复长解锁。
6. 系统接管/恢复失败要用完成结果记录，不提前宣称已恢复；短时未收敛不能立即视为写入失败，避免恢复循环震荡。

首个补丁不改曲线、温度临界值、既有安全兜底、用户配置、更新线路或安装完成页。执行验收应使用同一份 Swift 决策代码的假后端，而不是另写模拟控制器证明自己正确。对现有工具的实际写入和睡眠仍需 Beta 实机验证。

## 本轮结果

已确认：App 缺少系统睡眠/唤醒订阅；小差值判断依据上一命令而非控制权；现有工具已包含大小写模式选择、直接写模式/Ftst 回退和重试；系统恢复提示早于命令确认。

未确认：用户设备睡眠后的实际模式、工具报错、真实转速变化和完整故障原因。没有修改产品代码、运行构建或硬件控制，没有宣称修复已完成。
