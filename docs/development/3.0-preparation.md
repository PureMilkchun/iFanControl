## 当前架构及设计理由

| 各设置窗口 | 显示偏好即时生效；手动转速/安全转速点应用写配置 | 保留现有生效时机；“应用成功”当前是配置写入反馈，硬件实际 RPM 会由控制循环逐步达到 |
| HelpWindowController | 简介、诊断支持、FAQ、赞赏；版本与更新开关 | 简介有 108pt App 图标，其他页页头有 44pt 图标；普通菜单栏显示遥测文字，未显示 App 图标。隐藏入口应先确定指哪一个图标 |
| PowerTelemetryReader | IOReport Energy Model 差分算功率；SMC PDTR 读取 DC In | 初次只有能量基线，没有可显示功率；下一轮才有差分。IOReportBridge 声明系统接口，不等于自带可移植实现 |
| ThermalAnomalyAlertService | 10 分钟桶、低功率/高 RPM/高温规则；12 小时提醒冷却 | 至少 200 样本、480 秒跨度；两桶连续合格或近期四桶合格才提醒。它是观测提醒，不直接调速；离线 ML 实验未接入生产控制 |
| PrivacyStatsService | 匿名 ID、版本/build、15 分钟入队、日批量上传、离线保存 | 启动 flush、当前 build 成功确认与重试；积压按事件原版本分组；退出同步等待发送是明确设计。反馈已与心跳解耦 |
| FeedbackService/AppLog | 反馈限流、日志轮转、诊断导出、邮件撰写入口 | 日志支持远程诊断；诊断包与发布包不同，诊断包允许包含用户配置。打开邮件客户端不等于自动发送邮件 |
| InstallationCoordinator | App 内生成临时完整卸载脚本 | 用户不用保留原安装包；脚本等待 App 退出后继续删除文件；这是卸载链路，不能误复用于新更新 |

`hasProbedHardware = true` 必须保持在 profile 内的 `refreshTelemetry()` 之前，否则存在递归调用。历史 kentsmc semaphore 超时包装造成读取停滞并被回滚，本次不重引入。启动/profile 和少数恢复路径仍有同步读取，不能把“日常后台轮询”误写成“所有硬件 I/O 都已经异步”，也不能在 Beta 工作中顺手调整这些路径。

配置类型位于 FanCurveEditor 是当前模块依赖结果：主程序依赖编辑器并 typealias 导入。直接把 Config 移回 executable target 会让编辑器无法依赖它；今后抽模型需要独立公共 target。

## 更新的完整契约

当前路径：启动 30 秒后自动检查（开关开启时）或帮助页手动检查 → 请求 PKG manifest → 比较整数 latest_build 与当前 CFBundleVersion → 新版本提示“立即更新 / 稍后” → 确认后下载 PKG → HTTP 状态检查及 SHA256 校验 → UUID 临时目录原子保存 → NSWorkspace 打开系统安装器 → App 正常退出 → 用户完成系统安装 → 用户从应用程序打开。

- 自动检查没有定期 timer，没有 24 小时节流；last_check 仅记录时间。提交 `f95c414` 明确移除了节流，避免新版本发布后被旧检查时间挡住。
- 手动检查即使关闭自动检查仍可执行；自动失败保持安静，手动失败显示提示并提供 GitHub 入口。
- `mandatory`、`published_at` 存在于解码模型，当前未用于强制更新或提示策略；`rollout_percent`、`min_supported_build` 未参与客户端决策，不能推断已实现灰度/强更。
- 本阶段不加入预下载、不改变提示顺序；这是规划第三项的工作。
- legacy `update-manifest.json` 永久保持 2.9.9/build52，两个 legacy ZIP 固定内容和哈希；新的 stable/Beta 都使用 PKG。
- 新 stable manifest 是 `update-manifest-pkg.json`；官网版本展示和 `/download` 仍指 stable。当前 download handler 的 build 查询参数单独写在源码中，不自动读取 manifest。
- PKG 使用同一 App/bundle/package identifier、安装目录、kentsmc 与 sudoers 位置；preinstall 要求 App 已退出，postinstall 不从 root 安装进程启动 GUI，也不创建用户设置。
- 构建脚本展开最终 PKG 后验证资源、App/tool 哈希、脚本、代码签名、sudoers；不执行安装。组件设置 `BundleIsVersionChecked = true`，降级需要真实系统安装验证。
- SHA256 是现有完整性验证方式。保留“不增加文件大小校验”的项目约束；历史记录的 CDN 原因解释没有在本次独立复现。

## 第四项建议实现边界

这是建议，尚未写入业务代码或发布。

1. 解锁状态与更新偏好分开：点击指定 App 图标十次后露出开发者区域；解锁本身不自动订阅 Beta。Beta 勾选后，手动与启动自动检查都使用所选通道。
2. 开发者模式建议使用独立 UserDefaults key，保持跨启动/升级；提供明确退出入口。退出时关闭 Beta 偏好，重新隐藏区域。点击计数建议只在本次窗口会话累计，关窗未解锁则归零。
3. 引入 UpdateChannel/UpdatePreferences，stable 保持当前 endpoint，Beta 建议新 `update-manifest-beta.json`。Beta PKG 使用独立且带 build 的文件名，避免覆盖官网下载的 stable 包或旧 ZIP。
4. 将 UpdateService 从 main.swift 小范围提取，stable/Beta 共用 manifest 解码、版本比较、提示、下载、SHA256、系统安装器、正常退出和失败处理。不能靠另一份 updater 模拟“测试更新”。
5. 发布产物自身的 stable/Beta 身份与用户订阅通道分开存储。保持数字 CFBundleShortVersionString 和整数 CFBundleVersion，界面用额外字段显示 Beta 标签/序号。不要直接把 `3.0.0-beta.1` 写进系统版本字段。
6. stable/Beta 共用单调递增 build，例如 stable 52 → beta 53 → beta 54 → stable 55（示例，未占用版本号）。版本名仍需遵守原生安装器的版本规则；更高 build 并不能替代跨版本降级测试。
7. 普通通道只提供正式版本。Beta 通道建议在正式发布时也指向最终正式包，保证持续使用 Beta 路线的开发者可以收到正式发布；另一可选方案是订阅 Beta 时同时比较两份 feed，但必须明确采用哪种政策。
8. 现有失败链接按 `v{latestVersion}` 拼接。Beta tag 可能包含序号，建议 manifest 加可选 release_url 并保持 stable 默认兼容，避免下载失败后跳错 Release。
9. 检查开始时固定 channel，收到结果时确认 channel/偏好仍有效，防止检查过程中关闭 Beta 后出现旧 Beta 提示；下载与安装入口避免重复操作。只解决新增通道引入的状态关系，保持现有常规更新的可验证性。
10. Beta manifest 同样设置 no-store；Beta 发布校验应检查 feed、包、hash、App version/build/release 身份一致，并继续执行 legacy 固定通道校验。更新正式包时同步官网、stable feed、GitHub；发布 Beta 时保持正式下载入口与 legacy 资产不变。

Apple 的 [CFBundleShortVersionString 文档](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring)要求三段整数版本；[CFBundleVersion 文档](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion)说明数字构建版本及分发前递增。现有后台以 `version-build` 拼接并按 `-` 分割，因此预发布后缀还会影响后台解析；额外 Beta 显示字段可以避免本阶段被迫改统计契约。

切回 stable 需要明确含义：只改变后续检查通道，还是立即安装当前正式版。若 Beta build 大于 stable，现有比较会判为没有更高版本；不能把通道开关标成“已回到正式版”。自动降级会涉及原生安装器、配置兼容与真实验证，应作为明确需求处理。

## 合理的整理顺序

当前有两层独立 Git 仓库：父目录仓库管理官网/后台，当前目录有独立 App 仓库。不要直接移动整个主目录、合并 .git 或误以为在 App 仓库提交就会包含官网改动。父目录当前大量近期网站/后台文件尚未跟踪，建议先建立能够恢复的各项目版本基线，再讨论是否统一仓库。

### 随 Beta 功能做的小整理

- 提取 `Sources/MacFanControl/Updates/UpdateService.swift`，UpdateManifest 和新增通道/偏好保持同一目录；保留 target 结构及原业务行为。
- 在 `Tests/` 建立真实更新契约测试，接入 SPM/CI。目前 manifest 测试是 packaging 下独立 Swift 文件，CI 检查 Tests 目录，没有自动执行它。
- 明确 stable/Beta/legacy 发布清单，减少未来把 Beta 写到正式通道的机会。

这是目标结构，不是本次搬迁计划。先做机械拆文件并验证编译/运行，再做行为变化；跨文件 private 访问和 Swift actor 隔离必须随拆分核对。避免拆分、改 UI、改硬件策略、改 updater 同时发生。

当前 App 二进制、签名产物和图标仍在 Git 中，README 所称“只保留源码”不准确。建议先补可复现生成 App bundle 的脚本，确认 PKG 可从新输出路径构建，再停止跟踪可生成的 App/binary/signature。不能先删 App bundle，因为当前 PKG 构建依赖它。

`iFanControl-2.8.27` 仍有重复脚本/tool，部分 App 内容已在本次开始前被本地删除。根 icon 与现 App icon、两份 kentsmc 的 SHA256 分别相同，存在可消除的重复；但不要替用户恢复/完成那些删除，也不要删除线上冻结迁移 ZIP。当前记忆还引用已不存在的旧目录图标路径，应随资源来源整理修正。

离线 analysis 和 liquid-glass HTML 应标记实验状态，并与生产模块、发布输出分开；用户反馈/邮件记录也应从根目录生产工程文件中分离。这些文件是否归档/纳入跟踪由其用途决定，不能统一当垃圾删除。

## Stats 借鉴的边界

已核对上游 commit `0c0e551e199938a92af963c25a15a3ca1aef7764` 的 [传感器目录](https://github.com/exelban/stats/blob/0c0e551e199938a92af963c25a15a3ca1aef7764/Modules/Sensors/values.swift)和[读取器](https://github.com/exelban/stats/blob/0c0e551e199938a92af963c25a15a3ca1aef7764/Modules/Sensors/readers.swift)。Stats 保留机型平台标签和是否参与平均的标记，未知 key 独立分类；本工程目录合并了多平台 key，并按名称推断组件、动态候选参与当前选择。这是现有策略差异，并不能仅凭上游不同认定本工程错误。

第二项可以以后以“固定上游版本、带来源的平台/类别数据、真实读取夹具、失败/恢复场景”推进；仅复制一份最新 key 清单不能证明没有实机的兼容性。第四项无需改变硬件策略。
