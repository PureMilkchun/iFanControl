# iFanControl 3.0 UI 与全流程体验梳理

基线：2.9.10 Beta / build63。日期：2026-10-12至13日。

本轮完成现状盘点、原生窗口审视和改善设计。没有改动产品 UI 源码、控温规则、用户配置、安装包或线上发布。用户已确认通过 Beta 更新到63；配置和偏好的逐项保留结果尚未反馈，不能把这些结果一并认定通过。

## 设计目标

简洁：让用户少做无意义的选择，第一眼找到当前状态和下一步。必要的硬件状态与失败信息仍然可见。

优雅：操作有自然的起点、可理解的等待和明确的收尾。完成反馈的时机必须真实，留出用户看清结果的时间，再安静地回到工作状态。

高效：常用操作路径短，编辑与预览在同一处，后台刷新不打断交互，不让用户反复判断“到底生效了吗”。

PKG 已体现这三个目标：熟悉的系统安装步骤、克制的介绍、系统原生完成勾和完成后的打开指引。3.0 应把同等质量延伸到应用内的检查、等待、设置、异常及反馈流程。

## 审视方法与证据边界

- 阅读当前菜单、全部活跃窗口、弹窗/生命周期入口、曲线模块及 PKG 生成/安装脚本，并结合历史记录解释设计意图。
- 通过独立原生 App 加载当前 UI 类，实际查看中文浅色、部分深色和英文深色界面；观察连续/档位切换、应用完成反馈、空反馈验证、帮助导航、十次解锁和原生菜单。
- 测试 App 使用独立偏好域和配置目录；硬件数据为模拟值，不启动 AppDelegate 或控温轮询。反馈发送为本地替身，不向开发者发送消息。更新弹窗使用明确标注的样例，未下载/安装样例版本。
- 系统 Installer 实际打开63包，查看介绍、目的宗卷和安装类型，在安装按钮前停止并关闭。未重新安装，未为审视复演系统完成勾动画。该动画的体验由用户说明，包生成配置确认其被有意保留。
- 截图来自 CUA 原生窗口，不使用漏掉控件的离屏 cacheDisplay 图。系统强调色、指针高亮及窗口装饰不视为 App 自己设计的品牌元素。
- 官网下载入口已做源码盘点；浏览器工具超时，未完成本轮整站视觉审视。安装授权、完整卸载、故障弹窗的全套场景做了源码盘点，未对用户机器触发这些操作。

## 应当保留的现有设计

1. **系统安装器与完成勾。** `build.py` 有意不加入自定义 conclusion/readme；`render_open_hint.swift` 使用侧栏背景继续展示打开说明，保留系统完成反馈。postinstall 不以 root 身份启动 GUI 或创建用户设置，这也应保留。
2. **菜单一次构建、状态原地刷新。** 这是性能与交互稳定性的设计，不应在视觉改造中退回高频重建菜单。
3. **显示设置即时生效、曲线关闭保存、转速明确应用。** 分别对应展示偏好、曲线编辑和控制参数，差异有意义。统一的是提示方式，不是强行改成一种保存语义。
4. **目标 RPM 与实际 RPM 的区别。** 现有说明防止用户误认为轻微波动就是失败；“已应用”只能确认设置已被接受，不能伪称硬件必然达到精确数值。
5. **遥测失效占位及系统接管。** `--`、启动中、传感器丢失、交还系统有实际控制含义，不能为了视觉干净隐藏这些状态。
6. **隐藏开发者模式与独立 Beta 路线。** 继续保持普通用户默认入口和正式发布不变。
7. **作者的亲切语气。** 反馈与支持作者可以保留人格；调整信息密度和层级，无须把全部文案改成冷冰冰的术语。

## 关键发现与对应设计

### 1. 把更新流程的等待与完成接起来（第一轮）

当前“立即更新”之后，下载和校验期间没有可见进度。用户再次点击检查时服务会忽略重复请求，但界面也没有解释正在进行什么。PKG 后半段已有清楚、自然的完成体验，前半段尚未达到同一水准。

建议保留原生新版本确认，增加一个安静的更新状态区域，按真实阶段表达：

| 阶段 | 用户看到 | 完成条件 |
| --- | --- | --- |
| 检查 | 正在检查更新；当前路线 | manifest读取与解析成功 |
| 可用更新 | 版本、简短改动、更新/稍后 | 用户选择更新 |
| 下载 | 正在下载安装包；有总量时展示真实进度，无总量时显示活动状态 | 网络传输结束且HTTP成功 |
| 校验 | 正在验证安装包 | SHA256匹配 |
| 交接 | 即将打开系统安装器，应用将退出 | 系统安装器打开成功 |
| 安装 | 使用系统安装器的步骤、授权与进度 | Installer确认执行成功 |
| 完成 | 保留系统完成勾和打开说明 | 系统确认安装完成 |
| 再次启动 | 当前版本清楚可见；可考虑一次性的简短已更新反馈 | 实际运行版本符合本次更新目标 |

取消必须停止相应请求，使后续结果不再打开安装器；失败允许明确重试。不能用固定计时器模拟下载百分比，也不能在安装器刚打开时显示“更新成功”。本轮设计只改善现有主动更新过程，不引入计划中的自动预下载功能。

### 2. 常用设置让用户“看到结果，再作选择”（第二轮）

信息栏设置目前从180pt变为640pt高，组合选项完整，但每个例子只解释局部值。建议上方固定显示最终两行预览，下方用“上行/下行”的并列配置，内容与样式同组。默认给出清楚的可读组合，复杂组合仍保留在高级项里。切换显示密度时避免突兀的整窗高度跳变。

主菜单保留原生NSMenu，按任务整理层级。2026-10-13维护者明确确认：大反馈邀请框虽然不可直接输入、与“告诉开发者”指向同一窗口，但文本框外观本身用于鼓励用户反馈，必须保留。此前建议替换为普通轻量入口的判断已撤回；应保持外观与点击打开独立窗口的语义，再优化对齐和操作可达性。详见 [反馈邀请修正记录](3.0-ui-feedback-intent.md)。

### 3. 曲线和转速完成感统一，保存规则保留（第三轮）

手动/安全转速已有“✓ 已应用”，约1.2秒后以0.25秒淡出。这种原位、轻量反馈值得延续。应用后仍显示“取消”可能让人误以为会撤销，应让未应用编辑与已应用完成的含义清楚。

曲线应显示当前预设及编辑/保存状态，拖动点时数值更易读；保留双击重命名，并可提供更容易发现的重命名入口。切换预设会通知主程序切换曲线，关闭时才持久化整个编辑结果，不能把所有拖动误称为即时保存。保存成功只在真实写入后反馈，失败应保留编辑内容。

正向/反向是既有坐标显示选项，保持数据及默认选择，不因曲线视觉方向擅改规则。轴名称明确温度与目标RPM。当前窗口标题里的“v33”与产品build63混用，可把组件调试版本移至诊断信息。曲线点目前未出现在原生AX树，应补键盘和辅助功能访问，而不改变5点控制模型。

### 4. 支持、错误与长文案按任务分层（第四轮）

诊断页先给快速自检，再把“导出诊断→联系支持”的顺序接起来；完整卸载独立放置。诊断包导出成功后，用户应清楚文件在哪里、接下来做什么；该ZIP不应未经用户选择自动发送。

英文实际渲染中，`Diagnostics & Support`、`Support the Author`和`Export Diagnostics`被截断。中文看起来宽松并不能证明本地化完成；布局按更长文案验证。英文安全说明也逼近右边缘，应加入合理宽度、换行与边距。

反馈发送成功当前总是承诺回复，但邮箱是可选的，宜根据是否有联系方式调整收尾文案。限流当前写“服务器压力大”，实际是本地每小时5次限制，提示应准确。保留已有发送中按钮、失败后恢复发送和成功收尾；外部发送成功只能在接口确认后显示。

功率页的首次等待说明在数据显示后仍占据同样位置，可根据状态变成“读取中/刚刚更新/暂不支持”。分组件估算和DC In总计不是同一测量范围，不能为了图表整齐强迫二者数值相等。

### 已证实的说明差异：安全温度

窗口写95℃；实际 `criticalTemp` 为110℃，`calculateFanRPM` 在达到该门槛时施加兜底。提交 `e5f620f` 明确把95改成110，因此110不是本轮发现的控温bug。后续统一UI说明与实际策略，不把硬件规则改回95来迁就文案。遥测陈旧状态还参与保守转速下限计算，说明也应避免把整个保护策略缩成一个温度数字。

## 动效与完成反馈准则

- 设置切换、显示/隐藏内容和短反馈可以用短淡入淡出，重点是保持上下文位置稳定；常规状态不循环播放庆祝动画。
- 成功勾只表示真实完成的动作。配置保存、反馈送达、系统安装完成是不同事件，不共用一个过早触发的“成功”。
- 重要失败/保护状态持续可见，恢复后再自然回到正常状态；用户的编辑内容在失败时保留。
- 尊重减少动态效果设置；提供清楚静态状态。键盘、VoiceOver、深浅色、中文英文一起验收。
- Installer自己的完成动画不替换、不重新实现。避免自动从root安装脚本启动用户App；任何后续打开便利设计都需保持当前权限与安装边界。

## 实施顺序与验收

第一批：补齐检查、下载、校验、交接的可见状态，保留PKG完成勾；统一安全说明的真实语义与本地化布局。该批不做菜单整体重写、设备策略或预下载。

第二批：菜单按任务分组，保留主动反馈邀请框及其产品意图，改善信息栏组合预览。

第三批：曲线编辑状态、重命名可发现性、转速确认反馈与辅助功能。

第四批：关于/帮助、诊断、反馈、功率及首次使用/失败路径的细节统一。

每批单独进入Beta。下一可发布build大于63，正式线路维持2.9.9/build52。验收同时观察进入、等待、成功、失败、取消、重开和重启；在真实任务里确认更省心，再考虑正式发布。
